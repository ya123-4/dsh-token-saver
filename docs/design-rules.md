# dsh-token-saver 设计守则

给未来的维护者（包括我自己）：这个插件的每一个功能都必须过下面这几条。它们不是风格偏好，是**用真实账单换来的**。

---

## 一、缓存前缀稳定性（2026-10-17，最贵的一课）

**任何会改变"发给模型的请求前缀"的功能，先回答一个问题：**

> 第 N+1 步发出的请求，其前缀是否仍然是第 N 步请求前缀的**扩展**？

- ✅ **允许**：追加内容；在**稳定的集合**上做裁剪（集合一旦确定就不再随时间扩大）
- ❌ **禁止**：逐轮扩大删除/改写范围、依赖时间或轮次的动态裁剪、随机化

### 实测反例（不要重蹈）

`requestThinkingElision`（v0.3.0）每轮把"历史轮次"的 reasoning 删除范围扩大一段，看起来每轮只多删一点点，实际效果：

| 指标 | 关闭 | 开启 |
| --- | --- | --- |
| 缓存命中率 | **97.3%** | **78.3%** |
| 每步等效成本 | 38.9k | **121.4k（+212%）** |

逐步骤的关键帧：每个 turn 第一步 `input` 从几百 tokens 暴涨到约 40 万、命中率跌到 1–4%，同 turn 后续步才回到 99.9%。

**根因**：前缀每轮都被改写 → 每个 turn 边界付一次全量重建。

### 判断公式

```
重建代价 ≈ 改写后上下文大小 × 全价
每步节省 ≈ 删除的 tokens × (1 − 缓存命中单价)
回本步数 = 重建代价 / 每步节省
```

只有当**预计剩余步数 > 回本步数**时，改写前缀才可能划算。实测该功能的回本步数约 **25 步**，而一个 turn 只有 5–12 步 → 任何触发频率都亏。

### 正面对照

`schema 折叠` 为什么能赚？因为它折叠的集合**稳定**：同一批工具一直折叠，前缀只在工具目录真的变化时才变。这就是"稳定集合裁剪"与"逐轮扩大范围"的区别。

---

## 二、never-worse 双门控

任何替换都必须**同时**满足：内容真的变小（字节门）**且**估算 token 严格下降（token 门）。不满足就原样放行。不做"看起来应该更省"的改动。

## 三、fail-open

插件不能成为故障点：任何异常都回退到原始行为并记一条 warn。工具结果压缩失败 → 原样返回；schema 折叠失败 → 原样 assembly；请求改写失败 → 原样请求。

## 四、不改写权威记录

会话日志是唯一真相源。插件只能改**派生物**（发给模型的请求、呈现给模型的 schema），不能改日志本身。

- 例外只能是 DSH 官方提供的 surface 操作（`tool/result` 允许 replace，`assistant/message` 不允许 —— 见 README 杠杆 3）。
- 改请求属于"绕过可重建性约定"，必须默认关闭并显式记录风险。

## 五、明示省略

所有省略都带可见标记与数量，让模型能区分"工具没有输出"和"输出被省略"。绝不静默丢弃内容。

## 六、失败即熔断，不要重试

如果某个改动被上游明确拒绝（如 DSH 的 surface replace 校验），**一次拒绝就是证明**：立即熔断、停止重试、在 `token_saver_report` 里写明原因。沉默的重试会烧 CPU 和日志，还会掩盖问题。

---

## 附：功能复活前的检查清单

想重新打开某个已关闭的功能，先逐条打勾：

- [ ] 它是否改变请求前缀？若是，前缀是否**从某一点起永久固定**？
- [ ] 回本步数算过吗？小于典型剩余步数吗？
- [ ] 有 never-worse 门控吗？
- [ ] 失败会 fail-open 吗？
- [ ] 会在报告中暴露真实状态（而不是只报成功数）吗？
- [ ] 有能在真实数据上证明正收益的测量脚本吗？（`tools/cache-ab.mjs`、`tools/measure-*.mjs`）
